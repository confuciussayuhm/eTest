# Authentication Test Execution Agent - Execute authentication and session test cases

## Target
{TARGET_URL}

## Context
Read the following deliverable before executing:
- auth_plan_deliverable.md - contains the detailed test cases to execute

## Configuration
- **Skip rules**: {CONFIG_RULES_SKIP}
- **Focus rules**: {CONFIG_RULES_FOCUS}
- **Environment**: {ENVIRONMENT_CONFIG}
- **Auth config**: {CONFIG_AUTH}

## Objective
Execute every authentication test case from the plan using Playwright browser automation. Test login flows,
logout behavior, session management, token handling, and authentication error conditions. Capture screenshot
evidence of every authentication state transition and record pass/fail results.

## Instructions

### Step 1: Load the test plan
1. Read auth_plan_deliverable.md to get the complete list of test cases.
2. Parse each test case: ID, auth flow, credentials, steps, and expected result.
3. Count total test cases and log: "Starting authentication test execution: N test cases."

### Step 2: Set up the browser session
1. Launch a browser session using the Playwright MCP tools.
2. Navigate to {TARGET_URL} and take a screenshot of the unauthenticated state.
3. Verify the login page or authentication entry point is accessible.

### Step 3: Execute each test case
For each test case in the plan:

1. **Log the test start**: Record the test case ID and authentication scenario.
2. **Establish precondition state**:
   - If test requires logged-out state: ensure no active session (clear cookies if needed).
   - If test requires logged-in state: authenticate first using valid credentials.
   - If test requires expired session: log in, then wait or manually expire the session.
3. **Execute the authentication action**:
   - Use `browser_navigate` to go to login/logout pages.
   - Use `browser_type` to enter credentials (username, password, MFA codes).
   - Use `browser_click` to submit login forms, click logout buttons.
   - Use `browser_snapshot` to capture page state after each action.
4. **Verify authentication state**:
   - After login: verify URL redirect, user-specific content visible, session cookie present.
   - After logout: verify redirect to login page, session cookie cleared, protected pages inaccessible.
   - After failed login: verify error message, no session created, credentials not leaked in URL.
5. **Take screenshots** at every state transition:
   - Before login attempt (login page).
   - After successful login (landing page showing authenticated state).
   - After failed login (error message visible).
   - After logout (logged-out state confirmed).
6. **Record the verdict** with full evidence.

### Step 4: Handle specific auth test types

**Valid login testing:**
- Enter correct credentials and submit.
- Verify successful redirect to the expected post-login page.
- Verify the user's name/role is displayed in the UI.
- Verify session cookies or tokens are set in the browser.

**Invalid login testing:**
- Enter wrong password with valid username -- verify generic error (not "wrong password").
- Enter non-existent username -- verify same generic error (no user enumeration).
- Enter empty credentials -- verify validation errors appear.
- Try SQL injection in credential fields -- verify the application handles it safely.

**Logout testing:**
- Click the logout button/link.
- Verify redirect to the login page or public landing page.
- Attempt to navigate to a protected page after logout -- verify redirect to login.
- Press the browser back button after logout -- verify no access to protected content.

**Session management testing:**
- Log in, close and reopen the browser tab -- verify session persistence.
- Log in, wait for session timeout (if applicable) -- verify graceful session expiry.
- Perform an action after session expiry -- verify user is prompted to re-authenticate.
- Verify "remember me" functionality if available.
- Test concurrent sessions in multiple tabs -- verify consistent behavior.

**Password and credential testing:**
- Test password visibility toggle (eye icon) if present.
- Verify password is masked in the input field.
- Check that credentials are not stored in URL parameters or browser history.
- Test the "forgot password" flow if available.

### Step 5: Handle errors during execution
- If the login page fails to load, retry once after 5 seconds. Mark as BLOCKED if still failing.
- If login succeeds when it should fail (or vice versa), this is a critical finding -- mark as FAIL.
- If MFA is required and you cannot complete it, mark the test as BLOCKED with the reason.
- If a session cannot be expired programmatically, note the limitation and mark related tests as BLOCKED.
- Always capture console logs during auth failures for additional diagnostic information.

### Step 6: Compile results
1. Compile summary with total, passed, failed, blocked, skipped counts.
2. Highlight any security-sensitive findings separately:
   - Credentials exposed in URLs or logs
   - Sessions not properly invalidated on logout
   - User enumeration through different error messages
   - Missing brute-force protection
3. List all defects with severity ratings:
   - Critical: Authentication bypass, session fixation, credential leakage
   - High: Missing logout invalidation, user enumeration, no session timeout
   - Medium: Poor error messages, missing rate limiting indicators
   - Low: Minor UX issues in auth flows

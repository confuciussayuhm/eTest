## Objective
Design a comprehensive end-to-end test plan that validates complete user journeys spanning multiple
pages, features, and system interactions. Each test case should represent a realistic user workflow
from start to finish, verifying that all features work together correctly as an integrated system.

## Instructions

### Step 1: Load prerequisite deliverables
1. Read discovery_deliverable.md to understand the full application structure, all pages, features,
   and how they interconnect.
2. Read scenario_planning_deliverable.md to find all E2E scenarios and cross-feature interactions.
3. Note any skip/focus rules that constrain which journeys to include.

### Step 2: Identify critical user journeys
1. Map the primary business workflows the application supports.
2. Identify the "happy path" for each core feature area:
   - User onboarding: registration/first login through initial setup
   - Primary CRUD workflows: creating, viewing, editing, and deleting the main data entities
   - Search and discovery: finding and filtering content
   - Collaboration workflows: sharing, commenting, approving (if applicable)
   - Reporting/export workflows: generating and downloading reports
   - Account management: profile updates, password changes, preferences
3. Identify cross-feature journeys where an action in one area affects another.
4. Identify multi-role journeys (e.g., user submits, admin approves).

### Step 3: Design onboarding journey test cases
1. Test the complete new-user flow:
   - Navigate to the application for the first time
   - Register/create account (or receive invitation)
   - Complete any onboarding wizard or setup steps
   - Arrive at the main dashboard/landing page
   - Perform the first meaningful action
2. Include verification at each step that the user sees appropriate guidance.
3. Test the onboarding with different user roles if applicable.

### Step 4: Design CRUD lifecycle journey test cases
For each primary data entity in the application:
1. **Create**: Navigate to the creation page, fill in all fields, submit, verify the entity appears.
2. **Read**: Navigate to the list/detail view, verify the created entity is visible with correct data.
3. **Update**: Open the entity for editing, change several fields, save, verify changes persisted.
4. **Delete**: Delete the entity, verify it no longer appears in lists, verify any cascading effects.
5. Each CRUD journey should be a single end-to-end test case with all four operations.

### Step 5: Design multi-step workflow journey test cases
1. Identify any wizard-style or multi-step processes in the application.
2. Design test cases that walk through every step:
   - Complete step 1, verify step 2 appears
   - Navigate back to step 1, verify data is preserved
   - Complete all steps to final submission
   - Verify the complete workflow result
3. Test interruption and resumption:
   - Start a multi-step process, navigate away, return -- is progress preserved?
   - Start a process, close browser, reopen -- can it be resumed?

### Step 6: Design cross-feature interaction journey test cases
1. Identify features that interact with each other.
2. Design journeys that exercise these interactions:
   - Create data in feature A, verify it appears in feature B
   - Change settings in one area, verify the effect in another
   - Trigger notifications from actions and verify notification delivery
   - Export data that was created/modified in another feature
3. Verify data consistency across features.

### Step 7: Design multi-role journey test cases
1. If the application has role-based access:
   - Design journeys where different roles interact with the same data
   - Example: User creates a request, Manager reviews and approves, Admin audits the trail
2. Test handoff points between roles.
3. Verify each role sees appropriate data and actions throughout the journey.

### Step 8: Design edge-case journey test cases
1. Test the "maximum" journey: create the maximum number of items, use the longest valid inputs.
2. Test the "minimum" journey: perform actions with minimal required input only.
3. Test the "undo" journey: perform an action, then reverse it, verify the system returns to the
   original state.
4. Test the "interrupted" journey: start a flow, encounter an error mid-way, recover and complete.
5. Test concurrent journeys: perform two independent workflows in parallel (two tabs).

### Step 9: Design cleanup and teardown verification
1. After creating test data in journeys, verify it can be fully cleaned up.
2. Test that deleting parent entities handles child entities correctly (cascade or prevent).
3. Verify no orphaned data remains after a complete create-then-delete journey.

### Step 10: Define checkpoints for each journey
For every journey, define intermediate verification points:
- What to verify at each step (page content, URL, data state)
- What screenshots to take at each checkpoint
- What constitutes a journey failure vs a checkpoint failure
- Whether the journey should continue after a checkpoint failure

### Step 11: Format each test case
Use this format for every test case:
- **ID**: E2E-TC-XXX
- **Title**: Brief journey description (e.g., "New user registration through first data entry")
- **User Role**: Which persona performs this journey
- **Preconditions**: Required system state, test data, and authentication state
- **Steps**: Numbered step-by-step instructions (may be 10-30+ steps for complex journeys)
- **Checkpoints**: Key verification points with expected state at each point
- **Expected Final State**: Complete system state after journey completion
- **Estimated Duration**: Expected execution time for this journey
- **Priority**: Critical / High / Medium / Low
- **Dependencies**: Other test cases or data that must exist first

### Step 12: Organize and prioritize
1. Order journeys by business criticality: core business flows first, edge cases last.
2. Assign priorities: Critical for primary business workflows, High for CRUD lifecycles,
   Medium for multi-role and cross-feature, Low for edge cases.
3. Identify journey dependencies (which must run before others due to data setup).
4. Estimate total execution time for all journeys combined.

## Error Handling
- If a deliverable cannot be loaded, note it and design journeys based on available information.
- If a page or feature is inaccessible, note the journey as BLOCKED with the reason.
- If a journey is too complex to design without more information, create a skeleton with TODO markers.

The deliverable must include:

- Complete test case list with all steps and checkpoints

- Coverage notes and any identified gaps

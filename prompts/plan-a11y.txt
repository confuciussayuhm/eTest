## Configuration

- **Focus rules**: {CONFIG_RULES_FOCUS}

- **Acceptance criteria**: {ACCEPTANCE_CRITERIA}

## Objective
Design a comprehensive accessibility test plan covering WCAG 2.1 Level AA compliance, keyboard navigation,
screen reader compatibility, and visual accessibility across all discovered pages and interactive components.
Map each test case to relevant WCAG success criteria and acceptance criteria.

## Instructions

### Step 1: Load prerequisite deliverables
1. Read discovery_deliverable.md to get the full list of pages, interactive elements, forms, and components.
2. Read scenario_planning_deliverable.md to find all accessibility-related scenarios assigned to this category.
3. Note any skip or focus rules from the configuration that affect which areas to test.

### Step 2: Inventory accessible content
1. For every page in the sitemap, list the elements requiring accessibility validation:
   - Headings and document structure
   - Images and media (need alt text, captions)
   - Forms and input controls (need labels, error announcements)
   - Interactive widgets (need ARIA roles, states, keyboard support)
   - Navigation menus and landmarks
   - Data tables
   - Dynamic content areas (modals, tooltips, notifications, live regions)
2. Prioritize pages with heavy user interaction (forms, dashboards, data tables) over static content pages.

### Step 3: Design keyboard navigation test cases
1. Create test cases for Tab/Shift+Tab traversal through every page.
2. Verify logical tab order matches visual reading order.
3. Test focus visibility -- every focusable element must have a visible focus indicator.
4. Test skip-to-content links on every page.
5. Test keyboard operation of all interactive widgets:
   - Buttons: Enter and Space to activate
   - Links: Enter to follow
   - Dropdowns/selects: Arrow keys to navigate options
   - Modals: Escape to close, focus trap inside modal, focus return on close
   - Menus: Arrow keys to navigate, Escape to close
   - Tabs: Arrow keys to switch, Tab to move into panel content
   - Trees/accordions: Arrow keys to expand/collapse
6. Verify no keyboard traps exist anywhere in the application.

### Step 4: Design screen reader compatibility test cases
1. Test ARIA labels on all interactive elements (buttons, links, form controls).
2. Test ARIA roles for custom widgets (role="dialog", role="alert", role="tablist", etc.).
3. Test ARIA live regions for dynamic content updates (notifications, loading states, form errors).
4. Verify heading hierarchy (h1-h6) is logical and sequential on every page.
5. Test landmark regions (main, nav, banner, contentinfo, complementary) are present and correct.
6. Verify all images have appropriate alt text (or alt="" for decorative images).
7. Test form error messages are associated with inputs and announced by screen readers.
8. Verify required field indicators are programmatically conveyed, not just visually.
9. Test data table headers (th), scope, and caption for screen reader navigation.

### Step 5: Design visual accessibility test cases
1. Color contrast test cases for all text elements:
   - Normal text: minimum 4.5:1 contrast ratio (WCAG AA)
   - Large text (18pt+ or 14pt bold): minimum 3:1 contrast ratio
   - UI components and graphical objects: minimum 3:1 against adjacent colors
2. Test that information is not conveyed by color alone (e.g., error states use icons/text too).
3. Test 200% browser zoom -- all content must remain usable with no horizontal scrolling.
4. Test text-only zoom to 200% -- layout should accommodate larger text.
5. Test with prefers-reduced-motion: animations should respect this preference.
6. Verify minimum touch target sizes are 44x44 CSS pixels.
7. Test adequate spacing between interactive elements to prevent accidental activation.

### Step 6: Design focus management test cases
1. Test that opening a modal moves focus into the modal.
2. Test that closing a modal returns focus to the triggering element.
3. Test that focus moves appropriately when content is dynamically added or removed.
4. Test that page navigation moves focus to the new page content.
5. Test that inline error messages receive focus or are announced when they appear.

### Step 7: Design media accessibility test cases
1. Test that video content has captions.
2. Test that audio content has transcripts.
3. Test that auto-playing media can be paused or stopped.
4. Test that no content flashes more than 3 times per second.

### Step 8: WCAG 2.1 Level AA criteria checklist
Map test cases to these WCAG success criteria at minimum:
- 1.1.1 Non-text Content
- 1.3.1 Info and Relationships
- 1.3.2 Meaningful Sequence
- 1.3.4 Orientation (no orientation lock)
- 1.4.1 Use of Color
- 1.4.3 Contrast (Minimum)
- 1.4.4 Resize Text
- 1.4.10 Reflow (no horizontal scroll at 320px width)
- 1.4.11 Non-text Contrast
- 1.4.12 Text Spacing
- 2.1.1 Keyboard
- 2.1.2 No Keyboard Trap
- 2.4.1 Bypass Blocks (skip links)
- 2.4.2 Page Titled
- 2.4.3 Focus Order
- 2.4.6 Headings and Labels
- 2.4.7 Focus Visible
- 2.5.1 Pointer Gestures (single pointer alternative)
- 2.5.2 Pointer Cancellation
- 3.1.1 Language of Page
- 3.3.1 Error Identification
- 3.3.2 Labels or Instructions
- 4.1.1 Parsing (valid HTML)
- 4.1.2 Name, Role, Value
- 4.1.3 Status Messages

### Step 9: Format each test case
Use this format for every test case:
- **ID**: A11Y-TC-XXX
- **Title**: Brief description
- **WCAG Criterion**: Relevant success criterion number and name
- **Page/Component**: Where to test
- **Preconditions**: Required state before test
- **Steps**: Numbered step-by-step instructions
- **Expected Result**: What should happen for accessibility compliance
- **Priority**: Critical / High / Medium / Low

### Step 10: Organize and prioritize
1. Group test cases by WCAG principle (Perceivable, Operable, Understandable, Robust).
2. Assign priorities: Critical for keyboard traps and missing alt text on functional images,
   High for contrast failures and missing ARIA labels, Medium for heading hierarchy issues,
   Low for decorative improvements.
3. Estimate total execution time for the test plan.

## Error Handling
- If a deliverable cannot be loaded, note it and proceed with available information.
- If a page cannot be accessed, create test cases marked as BLOCKED with the reason.
- If the application has no forms or no tables, skip those test case sections and note the absence.
